# Divergences from the oracle

Known differences between mock-server and the oracle pinned in `oracle.env`. A row that is a to-do is a difference
still to be removed, not an accepted state; the oracle harness (`tests/oracle.rs`) ignores exactly these until they are
fixed. Three kinds of row are not to-dos: an upstream fix newer than the pinned oracle that mock-server adopts (its
"Why" cites the upstream commit; the row goes at the next re-pin that contains it), a difference the runtime causes,
which is deliberate (its "Why" begins `deliberate (`), and a difference no user can observe (its "Why" begins
`unreproducible:` and says why): a user who swaps the oracle's image for ours sees no functional change, because the
oracle itself varies run to run and ours is one of its outcomes, or because nothing can read the difference back. A
difference in console lines alone needs no row; one in an event-log entry or an HTTP answer does.
Every other row is a to-do, and its "Why" says what is not yet matched. What the last re-pin changed is listed per step
in `tests/scenarios/skips-rs.txt`. `conformance/coverage.py` counts the four kinds apart.

## Upstream nondeterminism (not divergences)

- **Match order after a clock step.** Upstream stamps `created = currentTimeMillis() - START + counter`
  (`Expectation.java:316`), so a wall-clock step backwards (seen once in the Docker VM while recording) reorders
  expectations created across it. mock-server uses a monotonic counter; goldens are recorded without clock steps.
- **Closest-match hint with several differing fields.** Upstream iterates a `HashMap` keyed by enum constants, whose
  order follows identity hash codes and changes per JVM run.
- **AsyncAPI Avro schema that is a bare undefined name** (`"foo"`): `Unknown schema: shaded_package.org.apache.avro.compiler.UnresolvedSchema_<n>`,
  where `n` counts every unresolved reference since the JVM started; mock-server counts per process.
- **Closing after a `respondBeforeBody` response.** `EarlyNettyResponseWriter` closes as soon as the response is
  written. Body bytes that reached the socket without being read make the kernel answer the close with a RST, so the
  client reads the response and then either the end of stream or `Connection reset`, depending on timing: measured
  2026-09-29 against the 8.0.0 jar as a host process, 150 of 200 exchanges reset when the client reads 30 ms after
  sending 1 KiB of body, and 7 of 200 (then 0 of 400) when it reads at once. mock-server half-closes and reads and discards the
  body until the client closes or 5 s pass (`http1::linger_close`), so the client always gets the response and then
  the end of stream. Upstream fix 88e72ebc7 (after 8.0.0) closes the same way (`LingeringClose`, 5 s); mock-server adopted its 5 s limit and its `connection: close`.
- **A tunnel whose loopback leg `maxInboundConnections` refuses.** `RelayConnectHandler.channelInactive` logs
  `tunnel connection to:{}closed before the tunnel was established, failing the proxy client request` or not, racing
  the limiter's reset of the loopback leg: 1 of 6 recordings on 2026-10-20; the limiter's own WARN for
  that refusal is suppressed within 10 s of the last one. mock-server serves the tunnel in-process, its loopback
  leg a counted slot, so it answers 502 (or the SOCKS failure) and logs no relay entry, the oracle's other outcome;
  scenario `inbound_connection_limit` reads the log after a refused CONNECT and a refused SOCKS4a CONNECT and masks
  only that WARN.

- **BouncyCastle's `ArrayIndexOutOfBoundsException` after JIT compilation.** A PEM key, CRL or certificate request
  whose reading ends in one carries the JDK's `Index i out of bounds for length n` (with that cause) until the JIT
  compiles the throwing method; then HotSpot throws a preallocated exception without message, cause or stack
  (`OmitStackTraceInFastThrow`), so the text reads `malformed data: null`, `encoded key spec not recognized: null` or
  a bare `ArrayIndexOutOfBoundsException`. Which form a step meets depends on JIT timing within the oracle's run.
  mock-server always gives the cold form; scenarios `idp_pem_crl_lazy`, `idp_pem_key_factory_errors` and
  `idp_pem_other_objects` mask both forms to one, and `keys::tests` checks the cold messages against
  BouncyCastle 1.86.
