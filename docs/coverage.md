## Known flakiness

Under heavy concurrent load (builds or recordings next to a run), a server process occasionally misses the 60 s readiness probe (seen once each for oracle-process and rs-process); the class passes when rerun alone. Runs are made one at a time.

The HTTP/3 classes that send a request body (`Http3McpIntegrationTest`, `Http3MockingMatrixIntegrationTest`) race in their own client, on the oracle as on mock-server: `requestStream.write(headers).sync()` is an unflushed write from the test thread, which Netty queues with `lazyExecute` (`AbstractChannelHandlerContext.java:832`, 4.2.17) without waking the event loop, so it waits for the next datagram or timer. When the server has sent its last packet before that, the next timer is the client's 30 s idle timeout: the test then fails after about 50 s (matrix) or 74 s (MCP) with no answer. Measured on Linux arm64 (2026-09-28) with that client: 10 of 300 requests stalled against the 8.0.0 jar, 9 of 300 against mock-server; unmodified `Http3McpIntegrationTest` failed this way on oracle-process too (1 run in 5). macOS does not show it. Not a server divergence; nothing in the server changes it without diverging on the wire.
